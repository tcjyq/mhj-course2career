# Course2Career 开发规范

## 1. 文档目的

本规范用于统一 Course2Career 的开发方式，使代码、提交历史、测试和文档能够体现真实的软件工程过程。规范适用于人工开发和 AI 辅助开发。

基本原则：

- 每次变更范围清晰、可以验证、可以回退。
- 先明确需求和验收标准，再实现功能。
- 大模型负责语义提取和建议，确定性业务规则由 Python 代码执行。
- 不提交密钥、用户隐私数据、临时输出或无法说明来源的数据。
- 不为一次性逻辑创建额外抽象；确认无用的代码直接删除。
- 代码、测试和文档应在同一个功能变更中同步更新。

## 2. Git 提交规范

### 2.1 提交格式

采用 Conventional Commits 风格：

```text
<type>(<scope>): <subject>
```

- `type`：提交类型，必须使用小写英文。
- `scope`：影响模块，可选，使用小写英文或连字符。
- `subject`：简短描述本次变更，使用中文，不加句号。

示例：

```text
feat(course-parser): 支持课程 Excel 字段校验
fix(scoring): 修复缺失技能参与加权的问题
test(jd-analyzer): 增加模型返回空技能列表测试
docs(readme): 补充本地运行步骤
refactor(llm-client): 统一模型异常转换逻辑
chore: 初始化项目目录结构
```

### 2.2 提交类型

| 类型 | 用途 |
|---|---|
| `feat` | 新增用户可感知的功能 |
| `fix` | 修复缺陷 |
| `docs` | 仅修改文档 |
| `test` | 新增或调整测试，不改变业务行为 |
| `refactor` | 重构代码，不新增功能、不修复缺陷 |
| `style` | 仅格式调整，不改变逻辑 |
| `perf` | 性能优化 |
| `build` | 依赖、构建或打包配置变更 |
| `ci` | GitHub Actions 等持续集成变更 |
| `chore` | 其他维护性变更 |
| `revert` | 撤销已有提交 |

### 2.3 scope 建议

优先使用项目已有模块名：

- `course-parser`
- `jd-analyzer`
- `skill-normalizer`
- `skill-mapper`
- `scoring`
- `learning-path`
- `report`
- `llm-client`
- `ui`
- `tests`
- `readme`

### 2.4 提交要求

- 一个提交只解决一个明确问题。
- 提交前必须检查变更内容，避免混入缓存、测试数据、日志和密钥。
- 功能代码与对应测试原则上放在同一提交中。
- 提交信息描述结果，不写“更新代码”“修改一下”等模糊内容。
- 大型变更应拆分为可独立验证的提交，但不能提交明显无法运行的中间状态到 `main`。
- 不使用提交历史代替文档；重要设计理由写入架构文档或 ADR。
- 禁止直接修改已经共享的历史；不得对 `main` 执行强制推送。

提交前检查：

```text
git diff --check
ruff check .
ruff format --check .
pytest
```

## 3. 分支管理建议

### 3.1 分支模型

本项目采用轻量化 GitHub Flow，不额外维护长期 `develop` 分支。

- `main`：稳定分支，始终保持可运行或处于明确的初始化状态。
- 功能分支：从最新 `main` 创建，完成后通过 Pull Request 合并。
- 功能分支应短期存在，完成合并后删除。

### 3.2 分支命名

格式：

```text
<type>/<short-description>
```

示例：

```text
feature/excel-import
feature/jd-skill-extraction
fix/invalid-score-range
docs/update-quick-start
test/scoring-edge-cases
refactor/llm-client-errors
```

分支名称使用小写英文，单词间使用连字符，不使用中文、空格或个人姓名。

### 3.3 推荐流程

1. 从最新 `main` 创建功能分支。
2. 在 `docs/requirements.md` 或 Issue 中明确目标和验收标准。
3. 小步实现并提交代码、测试和文档。
4. 本地运行格式检查和测试。
5. 创建 Pull Request，说明背景、变更内容、验证方式和已知限制。
6. 检查自动化测试和最终差异。
7. 使用 Squash Merge 合并到 `main`，保证主分支历史简洁。
8. 删除已合并的功能分支。

个人项目也建议在里程碑功能上使用 Pull Request，它可以保留需求、实现和验证过程，便于作品集展示。纯文档错别字等极小变更可以直接提交到 `main`，但仍需保证提交信息规范。

### 3.4 Pull Request 最低要求

PR 描述至少包含：

- 背景与目标。
- 主要变更。
- 不在本次范围内的内容。
- 测试或手工验证结果。
- 页面变化截图，如有 UI 变更。
- 风险、限制或后续任务。

## 4. Python 代码规范

### 4.1 基础格式

- 遵循 PEP 8。
- 使用 4 个空格缩进，禁止 Tab。
- 单行长度上限为 88 个字符。
- 使用 UTF-8 编码。
- 使用 Ruff 进行检查和格式化，不手工维护与工具冲突的格式规则。
- 删除行尾空格，文件末尾保留一个换行符。

### 4.2 命名

- 变量、函数和模块：`snake_case`。
- 类：`PascalCase`。
- 常量：`UPPER_SNAKE_CASE`。
- 私有实现：以下划线开头，如 `_normalize_score`。
- 名称应表达业务含义，避免 `data1`、`temp`、`handle_data` 等模糊命名。
- 代码标识符使用英文；面向用户的界面文字和项目文档默认使用中文。

### 4.3 类型与数据模型

- 公共函数必须标注参数类型和返回类型。
- 课程、岗位技能、技能证据和分析报告使用明确的数据模型，不使用无约束的多层字典在模块间传递。
- 外部输入必须在进入领域逻辑前完成校验。
- 不使用 `Any` 逃避类型设计；确实无法确定时应说明边界原因。

### 4.4 模块职责

- `app.py` 和 UI 层只负责输入、展示和流程触发，不放评分公式或 Prompt 拼接。
- 课程解析、技能标准化和评分应保持为可独立测试的模块。
- `llm_client.py` 只负责模型通信、超时和异常转换，不包含页面逻辑。
- Prompt 保存在 `prompts/`，不要把长 Prompt 散落在 Python 文件中。
- 权重、阈值和模型名称集中配置，不使用无说明的魔法数字。
- 领域逻辑优先使用无副作用的纯函数，便于测试和复用。

### 4.5 导入与依赖

导入顺序为：

1. Python 标准库。
2. 第三方库。
3. 项目内部模块。

不同分组之间空一行。禁止通配符导入。新增依赖前必须确认：

- 标准库或现有依赖是否已经能解决问题。
- 依赖是否仍在维护。
- 许可证是否适合公开仓库。
- 是否需要同步更新 `requirements.txt` 和 README。

### 4.6 异常与日志

- 禁止使用无类型的 `except:`。
- 只捕获能够处理或转换的异常。
- 面向用户的错误信息应清晰，但不能暴露 API Key、请求头或完整敏感输入。
- 领域模块抛出明确异常，由 UI 层转换为用户提示。
- 日志记录事件和上下文，不记录真实密钥、完整课程文件或未经脱敏的 JD。
- 超时和重试必须有上限，不能无限重试。

## 5. 文件命名规范

### 5.1 Python 文件

- 使用小写 `snake_case.py`。
- 文件名对应单一职责，如 `course_parser.py`、`report_exporter.py`。
- 测试文件使用 `test_<module>.py`。
- 不使用 `utils.py`、`common.py`、`misc.py` 作为无边界代码容器；应按业务职责命名。

### 5.2 文档和配置文件

- Markdown 文档使用小写连字符，如 `development-guide.md`。
- Prompt 文件使用小写下划线，如 `extract_jd_skills.txt`。
- JSON 数据文件使用小写下划线，如 `course_skill_map.json`。
- 环境变量使用 `UPPER_SNAKE_CASE`。
- 示例文件名应说明场景，如 `sample_data_analyst_jd.txt`。

### 5.3 目录命名

- Python 包目录使用小写英文，不使用连字符。
- 文档、数据和测试目录使用简短的小写英文。
- 不创建含空格、中文或版本后缀的源代码目录。
- 不保留 `old`、`backup`、`final_v2` 等目录；历史版本由 Git 管理。

## 6. 注释与文档字符串规范

### 6.1 注释原则

- 注释解释“为什么”和业务约束，不重复代码已经表达的“做什么”。
- 复杂评分边界、外部 API 限制和非直观兼容处理应说明原因。
- 代码变化时同步更新相关注释。
- 禁止保留被注释掉的旧代码，确认无用后直接删除。
- 不使用注释掩盖过长或职责混乱的函数，应优先改进结构。

示例：

```python
# 课程成绩只作为能力证据之一，不能直接等同于技能掌握度。
```

不推荐：

```python
# 计算总分
total_score = calculate_total_score(items)
```

### 6.2 文档字符串

以下内容需要文档字符串：

- 对外使用的类和公共函数。
- 有重要前置条件、异常或副作用的函数。
- 难以从名称看出业务规则的计算函数。

文档字符串应说明：

- 目的。
- 关键参数含义。
- 返回结果。
- 可能抛出的业务异常。
- 必要时给出边界说明。

简单私有函数如果名称和类型已经足够清晰，可以不写文档字符串。

### 6.3 TODO 与设计决策

- 不留下没有负责人或跟踪项的长期 TODO。
- 暂缓事项记录到 GitHub Issue 或开发日志，并说明原因和完成条件。
- 框架、数据模型、评分方法等难以逆转的决策，应在 `docs/decisions/` 中建立 ADR。
- ADR 不删除；决策变化时新增 ADR，并标记被替代关系。

## 7. 测试规范

### 7.1 测试层级

- 单元测试：验证课程校验、技能归一化、映射和评分等确定性逻辑。
- 集成测试：验证从课程和 JD 输入到分析报告输出的完整流程。
- AI 契约测试：验证模型响应是否符合规定结构，而不是要求每次文本完全一致。
- 手工 UI 测试：验证上传、错误提示、结果展示和文件下载。

### 7.2 文件与用例命名

- 测试文件：`test_<module>.py`。
- 测试函数：`test_<行为>_<条件>_<预期结果>`。
- 一个测试只验证一个主要行为。

示例：

```text
test_parse_courses_missing_required_column_raises_validation_error
test_calculate_skill_score_without_evidence_returns_zero
test_normalize_skill_mysql_maps_to_sql
```

### 7.3 编写要求

- 使用 Arrange、Act、Assert 结构组织测试。
- 测试必须可重复运行，不依赖执行顺序。
- 单元测试不访问真实网络、不调用真实大模型 API。
- 使用固定模拟响应测试模型成功、拒绝、超时和无效结构。
- 测试数据存放在 `tests/fixtures/`，不得包含真实个人信息。
- 优先测试边界条件和失败路径，不只测试正常输入。
- 修复缺陷时，先添加能够复现缺陷的回归测试。
- 不为了让测试通过而降低业务校验标准。

### 7.4 核心测试范围

至少覆盖：

- Excel 缺列、空值、重复课程和非法数值。
- 成绩、学分和自评分的边界。
- 中文、英文及别名技能归一化。
- 多门课程支持同一技能。
- 无课程证据、部分证据和强证据的评分。
- JD 无技能、重复技能和重要程度异常。
- 模型超时、拒绝、无效 JSON 和字段缺失。
- 报告中技能、证据和分数的一致性。

### 7.5 质量门槛

- 合并到 `main` 前，全部测试必须通过。
- 核心确定性模块建议保持至少 80% 语句覆盖率，但不为追求覆盖率编写无意义测试。
- AI 输出效果使用固定黄金样例评估，并记录 Prompt、模型和评测日期。
- 测试失败时禁止通过跳过测试或删除断言规避问题。

## 8. README 维护规范

README 是 GitHub 作品集的入口，必须与当前可运行状态一致，不能把计划功能描述成已经实现。

### 8.1 必备内容

README 应持续包含：

1. 项目名称和一句话定位。
2. 要解决的问题和目标用户。
3. 当前功能与项目状态。
4. 页面截图或演示 GIF。
5. 技术栈及选择理由。
6. 本地安装、配置和启动步骤。
7. 常用开发命令。
8. 项目结构和架构概览。
9. 示例输入和输出说明。
10. 测试方法和测试状态。
11. 隐私、安全和结果局限性。
12. 路线图、许可证和贡献方式。

### 8.2 更新时机

以下变更必须同步更新 README：

- 新增或删除用户可见功能。
- 安装、启动、配置或部署方式变化。
- 新增环境变量或外部服务。
- 项目结构发生明显变化。
- 技术栈或主要依赖发生变化。
- 示例、截图和在线演示地址发生变化。
- 已知限制或数据处理方式发生变化。

### 8.3 内容要求

- 所有命令必须在当前版本实际验证后再写入。
- 截图必须来自当前版本，不展示尚未实现的效果图作为成品。
- 不在 README 中放置真实 API Key、个人课程数据或招聘方敏感信息。
- 使用相对路径引用仓库内资源，定期检查链接有效性。
- README 保持面向使用者；详细评分、架构和评测内容链接到 `docs/`。
- 完成一个里程碑后同步更新项目状态、截图、测试结果和路线图。

## 9. 功能完成定义

一个功能只有同时满足以下条件才算完成：

- 需求和验收标准明确。
- 实现符合模块职责和命名规范。
- 正常路径、边界条件和主要失败路径有测试。
- Ruff 检查、格式检查和 pytest 全部通过。
- 没有提交密钥、临时文件或真实隐私数据。
- 用户可见变化已更新 README 或对应文档。
- 重要设计选择已经记录原因和取舍。
- `docs/development-log.md` 已记录本阶段结果和下一步。

本规范随项目演进维护。修改规范本身时，应使用 `docs` 类型提交，并在 Pull Request 中说明修改原因及对现有开发流程的影响。
