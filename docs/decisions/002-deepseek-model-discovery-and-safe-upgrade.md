# ADR 002：DeepSeek 模型发现与安全升级

- 状态：Accepted
- 日期：2026-08-06

## 背景

DeepSeek 模型目录会随供应商更新而变化。只在代码中固定一个模型 ID，可能在模型下线后导致系统 AI 突然不可用；直接选择目录中名称最新的模型，又可能把未经结构化输出、用量统计和中文 JD 评测的新模型自动投入公网。

## 决策

采用“运行时发现 + 已验证白名单 + 有界缓存 + 单次回退 + GitHub 监测”的组合方案：

1. `auto_safe` 模式调用官方模型目录，只从应用白名单与当前可用模型的交集中选择；
2. 按配置的优先顺序选择主模型，并保留其他已验证可用模型作为一次性 404 回退；
3. 目录结果按 API Key 指纹隔离缓存，不保存或记录 Key；目录故障时使用有效旧缓存，最终回退到固定模型；
4. 未知模型永不自动进入线上调用，GitHub 定时任务只创建待验证 Issue；
5. 每次调用记录供应商实际返回的模型 ID、Token 和费用；
6. 保留 `pinned` 模式及 `SYSTEM_AI_ENABLED` 紧急开关。

## 备选方案

- 永久固定模型：实现最简单，但模型下线时需要人工紧急改版。
- 自动选择目录中最新模型：更新最及时，但缺少兼容性和效果验证，不接受。
- 引入通用模型路由框架：当前只有少量供应商，增加依赖和运维复杂度，不采用。
- 定时任务直接修改白名单并部署：会绕过评测和人工审核，不采用。

## 影响

- 已验证模型之间的可用性切换可以自动完成；
- 新模型会被自动发现，但必须通过结构化契约、Token 用量、中文 JD 黄金集和回退测试后人工加入白名单；
- 部署环境需要将同一 DeepSeek Key 分别配置到 Streamlit Secrets 与可选的 GitHub Actions Secret；两处均不得写入仓库。
